# FlashProve-Next Lean 4 Formalization: Theorems and Assumptions (`lean/THEOREM.md`)

All 28 modules in [`lean/FlashProveNext/`](FlashProveNext) build on Lean 4.29.1 + Mathlib through [`lean/check.sh`](check.sh), which rejects any `sorry`, rejects `native_decide`, and rejects any axiom other than `propext`, `Classical.choice` and `Quot.sound`. The inventory below tracks **696 axiom-audited declarations** (each checked via `#print axioms` at the bottom of its module; helper structures and auxiliary definitions beyond the audited theorem inventory are noted per section where applicable).

**Shortest reading path.** Open [`FlashProveNext.lean`](FlashProveNext.lean) for the eight-layer map, then read the statements (not the proofs) of `SumcheckSound.sumcheck_sound`, `ConstrainedMask.constrained_mask_check_sound`, `BucketSampling.bucket_sampling_complete`, `MaskJoint.multiround_independent_causal` and `ProtocolBridge.fpn_protocol_lifetime_soundness`. Those five theorems carry the soundness, sampling, zero-knowledge and end-to-end claims; everything else feeds them. The executable bytes verifier (§2.1) is a separate, Mathlib-free layer: read `VerifyBytes.verifyBytes_refines_typed` and `Fpn2Rel3.verifyBytesRel3_refines_typed`. For what the end-to-end theorems about the executable verifiers assume, read §2.4 and the structure `Fpn2EndToEnd.CryptoAssumptions`.

**What `Rel3TypedVerify O pub prof c` says.** For hash oracles `O : Rel3Oracles` (`hFs` for the transcript, `hMerkle` for coset Merkle trees), there are a layout, a GKR end state `g` and a PCS end state `pf` such that:

1. `GkrSpec`: `root_num = 0` and `root_den ≠ 0`; layer 0 satisfies `num + α·den = eq(pt, [])·(n_l d_r + n_r d_l + α d_l d_r)`; each masked layer `k = 1..s` satisfies every round sum `g(0) + g(1) = claim` from the start value `num + α·den + λ·G_sum`, and the layer equation `claim = eq(pt, r)·(children) + λ·g_r`. The challenges `β, α, λ, r, branch` are squeezed from the transcript after absorbing the wire bytes of exactly the fields listed in spec §5.4.8.
2. `PcsSpec`: from the batched claim `Y` of spec §5.4.4 (`batchedClaim`, `rel3Terms`), all `n` degree-2 round sums `h(0) + h(1) = y` hold with the fold roots absorbed in wire order, and the last claim equals `FINAL · w̃(r)` (`weightsEval`).
3. `QuerySpec`: for each of the `Q` squeezed positions and each folded layer `t`, the coset leaf `B256_M(0x00 ‖ 4 values)` authenticates to `root_t` (`cosetRoot`), the value at the previous slot equals the previous `fold4` output for `t > 0`, and the last fold equals `FINAL`.

Each loop is stated as the relation `RunList` over per-step predicates (`GkrRoundSpec`, `GkrLayerSpec`, `PcsOpSpec`, `FoldSpec`, `QueryStepSpec`), and `runList_iff` plus the per-step lemmas show the executable loop decides it. The arithmetic the predicates mention (`lagrangeEval`, `eqEval`, `rel3Terms`, `weightsEval`, `fold4`) is the same executable code the verifier runs; Stage 2 does not give those functions an independent mathematical meaning.

**Raw wire bytes.** The verifier parses once with a `Codec` whose soundness proof gives `raw = encodeHeader ‖ encodeBodyRel3 c.body ‖ 0^pad`, and absorbs the encodings of the parsed sections. `encodeBodyRel3` is defined as the concatenation of exactly those sections in wire order, and `foldedBody_enc` / `layerBytes_sections` show the codec's encoder equals it, so every absorbed chunk is a slice of the accepted input.

The test BLAKE2b is not verified in Lean.

**What Stage 2 does not prove (left to later stages).** Stage 3 was spent on relation 4 and the dispatcher (below), so none of these items moved; instantiating the oracles with a random oracle and everything else here remain future stages, not assigned to a particular one. The open items are:

### 2.2 Concrete Goldilocks / $\mathbb F_{p^3}$ Soundness Bridge (M4 Stages 4–6, 8 and 9)

[`Fpn2Soundness.lean`](FlashProveNext/Fpn2Soundness.lean) (187 declarations, Mathlib) gives the field `E` of the soundness layer a concrete definition, proves that the executable verifier computes in it, and instantiates the abstract bounds at it. Write `p = 2^64 − 2^32 + 1` and `E = Fp3Field = AdjoinRoot (X^3 − 2)` over `ZMod p`.

| Group | Key Theorems | Statement |
|---|---|---|
| Prime and extension | **`goldilocks_prime`**, `goldilocksP_prime`, `goldilocks_two_not_cube`, **`fp3Poly_irreducible`**, **`fp3Field_card`**, `fp3Field_card_gt` | `p` is prime by the Lucas test with witness 7 over the factorization `p − 1 = 2^32 · 3 · 5 · 17 · 257 · 65537`. **How far this closes D11, and what it leaves open.** Before Stage 4, `fpn_protocol_lifetime_soundness` was only ever stated with `BadAcc`, `Fail`, `Doomed`, `Esc`, `hEsc` and `ProtocolRBRSpec` as free hypotheses. Stage 4 supplies one concrete, non-empty instance over the concrete field in which `hEsc` and the spec are theorems; Stage 5 removes the last assumed bound inside that instance (sampling) and completes the bytes-to-field transport (`root_den`, queries). It does **not** prove that `verifyBytesRel4` is sound. No theorem here has the form "an accepted false statement has probability `< ε`". The gaps, each stated in the module header:

* **Random oracle (ideal model).** The Fiat–Shamir hash stays an abstract function in `Fpn2Rel4`. The lifetime theorems model each oracle answer as an independent uniform element of `Rel4Ans k = E × E^k` and the prover as a non-anticipating state function. The statistical distance of `squeeze_fp3` (three 128-bit words reduced mod `p`) from uniform is not modelled, and the deployed sampler derives each draw from a 192-bit BLAKE2b word `U` through `⌊U C / 2^192⌋` (`protocol.py::draw_words`, `unit_index`), a seed space of size `2^192` rather than `p^3`.
* **Extraction (not proved).** The state function `st` of the lifetime theorems is arbitrary. That an accepting `verifyBytesRel4` transcript of a false statement forces some oracle answer into the escape set of a `Rel4Round`, which is the round-by-round "doomed state" argument for relation 4 including its Libra masks and the GKR layer reduction, is not formalized. `zcRound_accepts_shape` and its siblings are the first step of that argument (the executable round checks are `Accepts`-shaped over `E`), not the argument. The same applies to sampling: the premise of a sampling round (bad seeds have density `≥ σ`) defines the threshold class; that a false statement puts a prover in that class is the lineage / defect argument of [`specs/02`](../specs/02-soundness.md), not a Lean theorem here.
* **Statement semantics (not proved).** `rel4Terms`, `weightsEval`, `finalWeight4` and `batchedClaim4` are transported as opaque `Fp3` values; they are not shown to be multilinear extensions of the committed tables, and no Lean definition of the Plonkish relation of spec §5.5.1 exists. `rel4AlgNumer` is therefore a budget, not a quantity derived from the verifier; its `μ` term (`S + 16`) is an allowance with no instantiated lemma behind it.
* **Basefold / FRI proximity and Merkle binding (ideal, outside Lean).** Stage 5 transports the query equations to `E` and proves that `fold4` folds a cubic correctly. It does **not** prove a proximity gap for Reed–Solomon codes, that passing `Q` queries bounds the distance of the committed words, that the squeezed positions are uniform, or that `root_0`, `root_circ`, `root_t` bind the opened values (collision resistance of the Merkle hash). These stay assumptions (`A-PCS`, `A-ROM`). The `< 2^-150` figure is the algebraic (challenge-field) term only; the query term is governed by the profile's query count and is not bounded here. Stage 6 identifies `foldXInv` with the inverse of the domain point `ω_t^j` and the leaf slots with the coset `ω_t^j ι^k`, so `fold4Field_interpolates` now applies to the verifier's own constants; what it still does not give is (i) that the prover's encoder (`core/src/folded_air.rs`, `core/src/folded_gkr.rs`) lays the codeword out in this position order (golden vectors only), and (ii) any statement about words that are not low-degree: `fold4_foldXInv_interpolates` is the completeness direction of one fold on one coset, not a proximity or query-soundness bound.
* **Seed map and sampler (model, not the deployed sampler).** The Stage 4 gap "the `σ = 3/10` bound is assumed, `SpotCheck.frac_bad_bound` is not linked" is closed: the bound is derived for every `k` and `σ`. What remains: `Rel4Round.ofSpotCheck` takes an arbitrary seed map `u : E → B` and needs the *seed* share of `Bad`. `seedShare_of_fiber_ge` reduces it to the block share for a map with fibers of size `≥ c`, the gap between `c · |B|` and `p^3` being an explicit loss of threshold; no concrete seed map is constructed or proved near-balanced in Lean. The model draws `k` seeds independently and uniformly with replacement from one pool; the stratified, cost-weighted, lineage-padded sampler of `protocol.py::sample_request` is not linked to it (its pool and bias bounds are the abstract `LifetimeSoundness` / `RoundByRound` theorems of §2).
* **Rust / Python mechanical equivalence (not proved).** Agreement of the Lean verifier with `core/src/folded_air.rs` and the Python reference is by construction and by the 50 + 48 golden vectors, not by a mechanized proof about those programs.

Closed in Stage 5 (previously listed here): the query phase is now transported (`Rel4FieldEquations.query`), and `root_den ≠ 0` holds in `E` (`Rel4FieldEquations.root_den`).

Closed in Stage 6 (previously listed here): `foldXInv` is the exact inverse in `F_p ⊂ E` of the evaluation point `ω^(4^t · pos)` (`foldXInv_mul_domainPoint`, in `Fp3Field`: `foldXInv_mul_domainPoint_fp3`), `ω` has exact order `L`, and the registry holds the seventh profile `fpn2-folded-air-n20-v1` with its layout pin (`rel4Layout_foldedAirN20`: `g = 15`, `K = 32,768`, `S = 18`, `T = 10`, body `424,104` bytes) and algebraic error bound (`rel4_alg_error_foldedAirN20V1`).

### 2.3 Core IR Operator Translation Validation (M4-2, `Fpn2Gadgets`)

[`Fpn2Gadgets.lean`](FlashProveNext/Fpn2Gadgets.lean) proves, for six operator families of the gadget IR, that satisfying the constraint implies the integer (or rational / real) relation. **What M4-2 leaves open.**

* **Python IR to Lean correspondence.** The Lean hypotheses were written by reading `gadget_ir.py`, `arith.py`, `lower.py` and `microprogram.py`. No tool extracts the `Program` AST into Lean and no theorem says the emitted gates equal `MoeGates` or the two `LimbPlan` gates. A change in the Python emitter is not detected by `check.sh`.
* **Clauses of `topk_tau` and `attaining_rmx` not covered.** For `topk_tau`: the conclusion states a Boolean bitmap with exactly `top_k` ones and the pairwise $2\tau$ margin; it does not state `indices == sorted(selected)`, although the proof shows that the index cells are strictly increasing and enumerate the selected set. For `attaining_rmx`: one attaining selected argmax and `score ≤ maximum` on the selected set are proved; the weight clauses (`weight > 0` iff selected) and `denominator = Σ weight > 0` are not, and the gates `weight_positive`, `weight_zero`, `denominator` are not in `MoeGates`.
* **Row lowering.** `signed_lift_mul_add_sound` is one `AirRow`; `air_row_chain_sound` is the linear accumulator chain. The case analysis of `_gate_rows` itself (which gates take one row, how product rows and the chain are ordered, the `#pad` cell) is not modelled, and neither is the copy-constraint argument that makes the same cell appear in several rows.
* **Reference predicates are not verifier-checked.** `bf16_decode`, `norm_rsqrt` with the RMSNorm output enclosure, the `_exp_cell` weights, and the in-range Gated DeltaNet update `state = nearest(...)` stay `REFERENCE_PREDICATE` in the lowering. Families 3 and 5 and part (b) of family 6 are therefore statements about the predicate. `install_bf16` and `install_rsqrt` are reference lowerings that no production block installs, and their `.finite`, `.normalize` and `.tight` parts are lookups even there.
* **The Gated DeltaNet update is not the linear recurrence.** The production update is `nearest(decay·previous/scale + β·key/scale² · (value + convolution − key·decay·previous/scale²))`; its coefficient on `previous` is $(\mathit{decay}/\mathit{scale})(1 - \beta\,\mathit{key}^2/\mathit{scale}^3)$, not `decay/scale`. `state_box_propagation` takes $|\alpha_t| \le 1$ as a hypothesis. The gates give $0 \le \mathit{decay} \le \mathit{scale}$ (`gdn_decay_contraction`) and $0 \le \beta \le \mathit{scale}$, but `key` is only range-checked, so the second factor is not bounded by any gate.
* **`rmx` is the maximum of the selected experts.** `maximum_bound` is gated by the bitmap, as in `attaining_rmx`. It is the global maximum only at $\tau = 0$ or `top_k = experts`.
* **Selected branch only.** Families 4 and 6 are proved for selector $= 1$. That an unselected branch constrains nothing, and that exactly one selector is set (`exhaustive`, `boolean`, `unused`), is not formalized here.
* **Lift bound per gate.** Each lift theorem takes the bound on the integer value of the gate as a hypothesis. Lean does not recompute `Expr.bounds` interval arithmetic from the column widths, so that `check_bounds` establishes the hypothesis is not proved.
* **Lookup argument.** Table membership of a limb is a hypothesis (`l i < 128`). That the FracLogUp-GKR argument of relation 4 enforces it is the soundness question of §2.2, whose gaps are unchanged.
* **Completeness.** Only the direction constraint ⟹ relation is proved. That an honest witness satisfies the gates is exercised by the Python tests, not stated in Lean.

### 2.4 End-to-End Instantiation at the Executable Verifiers (M4-3, `Fpn2EndToEnd`)

[`Fpn2EndToEnd.lean`](FlashProveNext/Fpn2EndToEnd.lean) has 61 axiom-checked declarations (52 theorems and 9 definitions that carry proofs) and 27 further definitions and structures. It contains no `sorry`, no `native_decide` and no `axiom`; `autoImplicit` is off in the file.

**What it is, in one paragraph.** `Fpn2Soundness` instantiated `ProtocolRBRSpec` at a model whose bad event was defined as the escape event, so the three obligations of the structure held by construction. `Fpn2EndToEnd` defines the bad event from the executable verifier, `badAccept = { a | ∃ claim, verifyBytesRel4 (oracles a) (pub a) prof allowReduced (some root) (proof a) = .ok claim ∧ ¬ Statement claim }`, and builds `ProtocolRBRSpec` for that event from a record of explicit hypotheses, `CryptoAssumptions`. **Every lifetime theorem of this section is conditional on that record. None of them is an unconditional soundness theorem for `verifyBytesRel4` or `verifyBytesRel5`.** The record is a `structure`, passed as an argument: nothing is declared as an `axiom`.

#### The game and the bad event

`Sample k Q = Fin Q → Rel4Ans k` is the space of `Q` lazily sampled random-oracle answers (one challenge in `E` and `k` sampling seeds each); probabilities are counting measure on it. A `Rel4Game k Q W` is data: the profile and its layout, the pinned `circuitRoot`, and three maps from a sample to what the verifier sees, `oracles : Sample → Rel4Oracles` (the two hash functions), `pub : Sample → PublicInput`, `proof : Sample → ByteArray` (the adversary's output), plus a `cs : CompiledCS W` and a commitment relation `Commits : Rel4Claim → W → Prop`. `Statement claim` is `∃ w, Commits claim w ∧ cs.Satisfies w`. `Rel5Game` is the same with the weight pin. Nothing is assumed about this data; in particular the three maps are not derived from BLAKE2b, and the bias of `squeeze_fp3` is not modelled.

Three checks on the record:

* **No circular field, with one caveat.** No field mentions `badAccept`, and none is the path premise `hpath` of `RoundByRound` or a `ProtocolRBRSpec`. The caveat is `Fail`: it is free data, and nothing in the record stops it from containing `badAccept`. In that case `fail_bound` alone is the conclusion. So `Δ` is where all the unproved probability mass sits, and a record with a small `Δ` is exactly as hard to justify as the soundness of the protocol. `rel4Spec` derives the three obligations: `hInit` from a false statement, `extract_binds` and `ir_correspondence`; `hFinal` from `verifyBytesRel4_accept_field` and `pcs_proximity_final`; `hStep` from `verifyBytesRel4_accept_field` and `rbr_round_analysis`. * **Consistency.** `CryptoAssumptions.ofFailUniv` inhabits the record for every game at `Δ = 1` (take `Fail = univ`). So the record cannot be contradictory, and all of its content is in how small `Δ` is. This also means the record is only as credible as the claim that fields 6, 10, 11 and 12 hold outside an event of mass `2^-42`; that claim is not established in Lean, for relation 4 or for relation 5.
* **What is proved rather than assumed.** The per-round densities (`hEsc`) for all four kinds of round and any `k`, `σ`; the union bound over `Q` adaptive queries; the arithmetic `Δ + Q((1 − σ)^k + 2^-106) ≤ 2^-40` or `2^-20`; and the bytes-to-field step.

#### The zero-knowledge statement, exactly

The relation-4 joint mask is the block-triangular additive map on `(Libra mask (a_0, a), the 3 × 3 blinding cells of the ZK_ROWS = 3 rows in F_p, the scalar behind z_blind)` with values in `(Libra-masked round data, (e_a, e_b, e_c), blinded batched opening)`; `X1` and `X2` are arbitrary linear cross terms. `rel4JointMask_surjective` proves it surjective under four hypotheses: `2 ≠ 0`, the Libra challenge `ρ ≠ 0`, the coefficient `β ≠ 0` of the blinding scalar, and `hspan`: the `eq` weights `λ_0, λ_1, λ_2 ∈ E` of the three blinding rows at the zerocheck point span `E` over `F_p`. Then, for every witness-dependent shift `S`:

* `rel4_joint_view_independent`: the number of masks that produce a given view is the same for any two witnesses;
* `rel4_joint_view_uniform`: it equals the size of the kernel of the mask map, for every witness and every view. A simulator that outputs a uniform element of the view space has the distribution of the real linear view.

`rel5_joint_view_independent` / `_uniform` are the same for relation 5 with the Libra mask of the inner-product sumcheck and the scalar behind `z_blind` (`Libra + z_blind`). `rel4_joint_view_fp3` instantiates `K = F_p`, `E = F_p[X]/(X^3 − 2)` and discharges `2 ≠ 0`; `ρ ≠ 0`, `β ≠ 0` and `hspan` stay hypotheses (a point where the three weights are `F_p`-dependent is not excluded by the theorem; with fewer than three blinding rows `hspan` cannot hold, since `E` has dimension 3 over `F_p`; that remark is not a Lean theorem).

**Outside these theorems:** the non-linear messages (GKR inner-layer messages and the round polynomials as functions of earlier challenges, which rest on the mask-leaf and Libra arguments of `specs/03`), the Merkle openings and query-phase values, the simulation of the random oracle (programming), the map from the deployed prover's randomness to the abstract mask cells, and more than one transcript. The per-transcript rank certificate `require_joint_mask_air` of `specs/11` §5.5 is a Python computation, not a Lean theorem; `hspan` is the Lean-side counterpart of one of the conditions it checks. `ConstrainedMask` is a binding lemma for decoding masks (a row that differs from the honest one passes the multilinear check on at most `2^-186` of the points, `constrained_mask_binding_fp3`); it is a soundness statement and plays no part in the view-independence proof. `BucketSampling` concerns the sampler of the decoding relation and is not used by the relation-4 / relation-5 verifiers; the sampling term of the lifetime bounds comes from `SpotCheck.frac_bad_bound` through `Rel4Round.spot`.

## 3. What Lies Outside Lean

Every theorem above uses only Lean's three standard axioms; its hypotheses are explicit in its statement (in particular, `fpn_protocol_lifetime_soundness` takes `ProtocolRBRSpec`, per-round escape bounds `hEsc`, and spot-check miss `hm` as hypotheses; §2.2 discharges them for one concrete model over `E`, including the spot-check miss for every `k` and `σ`, not for the deployed verifier; §2.4 builds `ProtocolRBRSpec` for the bad-accept event of the executable verifiers from the record `CryptoAssumptions`, whose twelve fields are listed there). Connecting these theorems to the deployed protocol rests on the following obligations, catalogued in full in [`specs/07-assumptions-and-lean.md`](../specs/07-assumptions-and-lean.md):

1. **Cryptographic premises (`A-ROM`, `A-AROM`, `A-PCS`, `A-PCS-fold`, `A-CA`, `A-PRG`).** `H_out` (BLAKE3 / SHA-3) is modelled as a programmable random oracle; the width-12 Poseidon2 permutation as an ideal invertible permutation, with straight-line extraction for in-circuit sponges; Stage 1 rate-$1/4$ Basefold (`Q=168`) as round-by-round sound in the unique-decoding regime (its query arithmetic is checked in `basefold_qry_esc_le`), while v1.0 rate-$1/8$ multi-size layer-injected openings at `Q=72/100` rely on provisional Johnson/list-decoding proximity (`A-PCS-fold`; unique-decoding alone at rate $1/8$ requires `Q >= 128`), with per-request KV matrices using Reed–Solomon correlated agreement `A-CA`; and AES-256-CTR under ephemeral keys as a pseudorandom generator for mask regeneration.
2. **Constraint-compiler instantiation (`CompiledCS`).** `ProtocolBridge` proves the reduction from the abstract specification `ProtocolRBRSpec` (`P-ext`, `P-compile`, `P-loc`, `P-final`) to `RoundByRound.rbr_default_lifetime`. `Fpn2EndToEnd` (§2.4) instantiates `CompiledCS` at a Plonkish system given as Lean data and builds `ProtocolRBRSpec` for the executable verifiers from the hypotheses of `CryptoAssumptions`; it does not prove those hypotheses. That the concrete Python circuit builder implements `ProtocolRBRSpec` is argued on paper ([`specs/01`](../specs/01-relation.md) §4.5, [`specs/02`](../specs/02-soundness.md) §2.2) and exercised by 33 white-box forgery and tamper checks, not mechanically extracted from Lean.
3. **Field equations versus natural-number statements.** Several gadgets are proved over `ℕ` or `ℤ` while the circuit enforces them in the field. The one-hot selector in `ConstrainedMask` is the clearest case: the circuit checks `∑_q oh(q) = 1` and `∑_q q · oh(q) = q⋆` in `E`, and the Lean statement takes them over `ℕ`. The two agree because both sides are below `Q² ≪ p`; this is the small-value embedding of `StdAlgOps.intCast_inj_small`, applied in the prime subfield of `E`.
4. **Kernel rounding contract (`H-contract`) and floating-point propagation.** Deployed kernels are assumed to obey the per-operator rounding contract committed in `model_id`; this affects completeness only. The real-valued error-propagation formulas ([`specs/06`](../specs/06-tolerance-and-cheats.md) §2.2) are proved on paper and measured with zero honest violations across 392,928 blocks on `Qwen3-0.6B` and `Llama-3.2-1B-Instruct` ([`benchmarks/certified/`](../benchmarks/certified/README.md)). A floating-point scan template for linear attention is future work.
5. **Multi-proof zero knowledge.** `Mask` and `MaskJoint` prove exact transcript uniformity for one proof, including causal multi-round masking. The hybrid argument over many proofs, the random-oracle programming collision bound $q_H N_{\rm prog}/2^{256}$ and the keyed-sponge PRF bound are proved on paper in [`specs/03-zero-knowledge.md`](../specs/03-zero-knowledge.md).

## 4. How to Build and Verify

Requires Lean `4.29.1` (`elan` reads [`lean-toolchain`](lean-toolchain)) and, for the relation-3, relation-4 and relation-5 vector runs at the end of `check.sh`, `python3`:

```bash
cd lean
lake exe cache get
bash check.sh
```

Expected last lines: `OK: Lean verifyBytesRel3 agrees with all 48 golden vectors`, `OK: Lean verifyBytesRel4 agrees with all 50 golden vectors (50/50; the file holds 50)`, `OK: Lean verifyBytesRel5 agrees with all 33 golden vectors (33/33; the file holds 33), all 9 profile pins hold`, `OK: multi-tile relation 5 (beta = 2, 4 tiles): 26/26 cases, non-empty r_b squeeze equal to the prover's`, then `OK: all 28 modules verified, no sorry, only standard axioms` (exit code `0`). A vector mismatch makes `check.sh` fail, and so does any `native_decide` in the modules or test harnesses. Set `FPN_SKIP_VECTORS=1` to skip the vector runs.

The bytes-verifier modules need only the `lean` binary (no Mathlib, no `lake`), so the vector runs also work alone:

```bash
python3 lean/tests/check_rel3_vectors.py
python3 lean/tests/check_rel4_vectors.py
python3 lean/tests/check_rel5_vectors.py
```
